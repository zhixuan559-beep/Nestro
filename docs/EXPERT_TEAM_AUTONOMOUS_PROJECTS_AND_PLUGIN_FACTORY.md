# 专家团自主项目协作与 AI 插件创造能力

状态：需求与架构约束已确认；现有实现仅有部分基础，功能尚未完成。不得把本文档视为代码已落地或验收通过。

## 一、专家团双模式

### A. 用户手动协作模式
- 用户自行选择专家、指定各自任务、设置先后依赖或并行关系。
- 用户可以随时调整任务、暂停/恢复/取消成员工作，向单个专家或全体发送消息。
- 专家输出、交接、讨论、修改版本均进入同一项目工作区，用户可以点开查看。
- 用户可选择由主模型汇总，也可自行查看和组合各成员成果。

### B. 主模型自主项目模式
- 用户用自然语言提出项目目标；主模型先判断这是普通问答、单项工具任务还是需要专家团的项目型任务。
- 若适合专家团，主模型负责选择/组建团队、拆解工作包、定义交付物、依赖关系和验收标准，再将任务分派给适合的专家。
- 无依赖的工作包并行执行；有依赖的工作包按 DAG 顺序执行。不能把所有成员简单串行调用，也不能无约束地全量并发。
- 每名专家拥有独立任务上下文、角色指令、输入资料和产出；需要协作时可向其他成员发起有记录的请求/交接，其他成员的答复回到共享工作区。
- 专家完成后提交结构化成果（结论、证据/来源、产物、风险、未解决项、版本）；主模型负责交叉审查、识别冲突、要求返工或补充，最终整合成品并向用户交付。
- 主模型是项目总负责人和最终交付出口；专家成员不能绕开权限系统自行执行未授权操作。

## 二、专家团可视化工作区
- 项目级工作区可从聊天任务进入，支持用户点开查看全过程。
- 至少呈现：项目目标、主模型计划、任务 DAG、成员分工、队列/运行/阻塞/完成状态、成员消息与交接、工具调用记录、阶段成果、审查意见、最终成品。
- 事件流需要持久化，不能只依赖 Compose 临时状态或一段最终摘要；换会话/重启后仍可恢复查看。
- 用户可在工作区向某个成员或全体发送消息，调整任务、批准需要确认的动作、暂停/恢复/取消。
- 记录每条事件的 taskId、projectId、memberId、时间、类型、关联任务/消息/产物版本；对敏感内容按项目权限过滤。
- 进度回调只是 UI 更新入口，不等于完整的协作消息系统。

## 三、AI 自主创造插件
- 区分 Skill、Plugin、MCP：Skill 是提示词/流程能力；Plugin 是 Nestro 可安装、可版本化、可调用的可执行能力包；MCP 是外部工具服务接入协议。三者可统一发现和调度，但生命周期和安全边界不能混为一谈。
- 主模型发现现有能力不足时，可以提出插件方案；在允许的创作权限下生成插件 manifest、输入/输出 schema、实现代码/声明式工作流、依赖清单、权限声明、测试与说明。
- 插件必须在隔离沙箱或受限宿主 API 中运行，不得默认获得任意文件、网络、设备或账户权限；权限按最小必要原则声明，并按工具调用逐次校验。
- 创建流程：需求分析 → 插件草案 → 源码/定义生成 → 静态检查与依赖审查 → 沙箱测试 → 权限与影响预览 → 用户批准安装/启用 → 注册到统一能力目录 → 运行监控。
- 插件生成和安装分离。模型可以生成草案，但不能绕过用户批准自行安装高风险能力；外部网络、设备控制、数据写入、付费操作等需显式权限与确认。
- 插件有唯一 ID、语义化版本、签名/来源、依赖锁定、权限清单、审计日志、启停、升级、降级、卸载和回滚能力。
- 插件输出是不可信数据；插件不得修改自己的权限、信任根或审批状态。插件更新需重新检查和授权。
- 允许插件组合已有工具；新插件不能绕过 AgentToolCatalog、AgentRuntime、AgentPermissionRouter 和统一调度器。
- 不允许把“生成一个专家 prompt/Skill”冒充“创造可执行插件”。

## 四、统一架构约束
- 主模型负责理解意图、判断直接回答/单工具/专家项目、规划与最终综合。
- AgentTaskCoordinator 负责任务生命周期、队列、取消/恢复；共享 AgentToolCatalog 负责能力发现；AgentRuntime 和权限路由负责受控执行。
- 专家任务、消息事件、交接、产物与插件资产均需 project-scoped，并复用现有 ProjectResourceScopeStore / ProjectAccessControlStore。
- 所有专家和插件的工具调用都必须通过统一能力目录和运行时，不得各自绕过基座。
- 支持不同模型服务商；专家可配置模型策略，但预算、速率限制、并发上限、超时、重试和取消由统一策略控制。

## 五、当前源码核查结果（2026-11-22）
- ExpertTeamEngine.run() 已有 2–4 名专家的受限并行执行能力。
- ExpertTeamEngine.runCollaborative() 是一个专家开始、按 [[DELEGATE: ...]] 逐个交接的链式模式。
- ExpertTeamExecutionCoordinator.execute() 当前实际调用 runCollaborative()，所以聊天触发的专家团不是自主并行项目分工。
- NestroApp.kt 当前将专家状态回调写入临时 UI 状态，并保存 ExpertTeamRunHistoryCodec 结果；尚未发现完整持久化成员间消息事件、任务 DAG、交接线程和可交互项目工作区。
- 当前聊天只在用户已启用任务模式且已明确选中团队时，才把 expert_team.run 暴露给模型；主模型还不能自行选择/组建合适团队并自动启动项目。
- CapabilityDraftCoordinator 当前只生成 expert/skill 的 name+prompt 文本草案；未发现可执行 Plugin manifest、插件运行沙箱、安装/升级/撤销生命周期。因此 AI 自主插件创造尚未实现。

## 六、实施验收清单
- [ ] 手动模式支持用户逐成员派单、依赖设置、消息沟通、介入与控制。
- [ ] 自主项目模式由主模型规划、选人/组队、拆分工作包、设置验收标准。
- [ ] 专家无依赖任务并行执行，有依赖任务按 DAG 调度。
- [ ] 成员之间有可追踪消息、请求、交接与答复。
- [ ] 专家成果结构化版本化，主模型可审查、返工、冲突消解并整合交付。
- [ ] 项目工作区可见完整事件流，重启后可恢复。
- [ ] 模型可生成可执行插件包，而不只是 Skill/专家提示词。
- [ ] 插件有沙箱、manifest/schema、依赖与权限审查、测试、批准、注册和审计。
- [ ] 插件支持启停、升级、回滚、卸载和撤销信任。
- [ ] 专家团和插件所有执行统一通过 AgentRuntime/权限路由/能力目录。
