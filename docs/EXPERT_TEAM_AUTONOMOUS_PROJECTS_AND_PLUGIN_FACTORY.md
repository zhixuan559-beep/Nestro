# 专家团自主项目协作与 AI 插件创造能力

状态：需求与架构约束已确认；现有实现仅有部分基础，功能尚未完成。不得把本文档视为代码已落地或验收通过。

## 一、统一专家协作系统：两种入口，不是两套模式

专家协作只有一套团队、任务、消息、工具权限、执行调度和交付系统。用户可以从两个入口进入同一套系统：

### A. 主聊天入口：主模型自动组队
- 主聊天模型是常驻入口。用户只需描述目标或上传资料，不要求用户预先理解专家目录、Skill 或工作流。
- 主模型先查询当前项目可用专家、专家角色指令、Skill、工具能力和媒体处理能力，判断请求属于普通对话、单项工具任务，还是需要专家协作的项目任务。
- 普通问题直接由主模型回答；单项任务直接调用统一工具调度；项目任务由主模型创建临时团队或复用已有团队。
- 主模型拆解项目目标、选择专家、分配工作包、定义依赖关系、交付物和验收标准。无依赖任务并发，有依赖任务按 DAG 执行。
- 专家完成后提交结构化成果；主模型负责交叉审查、发现冲突、安排返工/补充，整合最终成品并向用户交付。
- 临时团队可以任务结束后解散，也可以保存为长期团队/项目空间。

### B. 专家中心入口：用户主动组队
- 用户主动进入专家中心，自行选择专家、上传资料、描述目标，也可以为成员分别指定任务。
- 后续仍使用同一套项目任务、DAG 调度、专家消息、工具权限、成果审查和主模型交付系统。
- 用户可以随时加入讨论、向单个专家或全体发消息、调整任务、暂停/恢复/取消；无需切换另一套执行模式。

### 团队内部真实协作
- 专家成员拥有独立角色、任务上下文、输入资料和成果；可以发起有记录的协作请求/交接，目标成员执行后把答复返回共享工作区。
- 运营师拆解项目时，可以把剪辑工作交给剪辑师；剪辑师提交成品后，运营师验收，再把后续工作交给文案师。依赖关系由主模型规划，不要求所有专家都同时启动。
- 用户可以点开团队工作区查看任务图、成员状态、消息/交接、工具调用、阶段成果、审查意见和最终交付。
- 主模型是项目总负责人和最终交付出口；专家不能绕开权限系统自行执行未授权操作。

## 三、AI 自主创造插件
- 区分 Skill、Plugin、MCP：Skill 是提示词/流程能力；Plugin 是 Nestro 可安装、可版本化、可调用的可执行能力包；MCP 是外部工具服务接入协议。三者可统一发现和调度，但生命周期和安全边界不能混为一谈。
- 主模型发现现有能力不足时，可以提出插件方案；在允许的创作权限下生成插件 manifest、输入/输出 schema、实现代码/声明式工作流、依赖清单、权限声明、测试与说明。
- 插件必须在隔离沙箱或受限宿主 API 中运行，不得默认获得任意文件、网络、设备或账户权限；权限按最小必要原则声明，并按工具调用逐次校验。
- 创建流程：需求分析 → 插件草案 → 源码/定义生成 → 静态检查与依赖审查 → 沙箱测试 → 权限与影响预览 → 用户批准安装/启用 → 注册到统一能力目录 → 运行监控。
- 插件生成和安装分离。模型可以生成草案，但不能绕过用户批准自行安装高风险能力；外部网络、设备控制、数据写入、付费操作等需显式权限与确认。
- 插件有唯一 ID、语义化版本、签名/来源、依赖锁定、权限清单、审计日志、启停、升级、降级、卸载和回滚能力。
- 插件输出是不可信数据；插件不得修改自己的权限、信任根或审批状态。插件更新需重新检查和授权。
- 允许插件组合已有工具；新插件不能绕过 AgentToolCatalog、AgentRuntime、AgentPermissionRouter 和统一调度器。
- 不允许把“生成一个专家 prompt/Skill”冒充“创造可执行插件”。

## 四、统一架构约束
- 主模型负责理解意图、判断直接回答/单工具/专家项目、规划与最终综合。
- AgentTaskCoordinator 负责任务生命周期、队列、取消/恢复；共享 AgentToolCatalog 负责能力发现；AgentRuntime 和权限路由负责受控执行。
- 专家任务、消息事件、交接、产物与插件资产均需 project-scoped，并复用现有 ProjectResourceScopeStore / ProjectAccessControlStore。
- 所有专家和插件的工具调用都必须通过统一能力目录和运行时，不得各自绕过基座。
- 支持不同模型服务商；专家可配置模型策略，但预算、速率限制、并发上限、超时、重试和取消由统一策略控制。

## 五、当前源码核查结果（2026-11-22）
- ExpertTeamEngine.run() 已有 2–4 名专家的受限并行执行能力；本轮新增每位成员独立 assignedTask，并在 MANUAL_PARALLEL 模式下使用各自任务提示词。
- ExpertTeamEngine.runCollaborative() 是一个专家开始、按 [[DELEGATE: ...]] 逐个交接的链式模式。
- ExpertTeamExecutionCoordinator.execute() 现支持 MANUAL_PARALLEL 与 SEQUENTIAL_DELEGATION 两种执行策略；但现有聊天入口尚未提供逐成员派单 UI，且默认仍走链式协作。自主项目模式的主模型任务拆解与 DAG 并行调度尚未接入。
- NestroApp.kt 当前将专家状态回调写入临时 UI 状态，并保存 ExpertTeamRunHistoryCodec 结果；完整持久化消息事件、任务 DAG、交接线程和可交互项目工作区尚未接通。本轮新增事件模型/codec 与可注入 sink，但还没有 Room 持久化实现或 UI 订阅入口。
- 本轮已将当前项目中至少有 2 名启用专家作为 expert_team.run 的可用条件；主聊天上下文会附带项目可见专家目录，主模型可在不要求用户预选团队的情况下提交成员名单和项目 DAG 计划。显式选中的团队仍优先作为成员范围。
- CapabilityDraftCoordinator 仍只生成 expert/skill 的 name+prompt 文本草案。本轮新增 GeneratedPluginFactory：模型可基于当前 AgentToolCatalog 生成声明式插件包，包含 SemVer、输入字段、步骤和工具参数；验证器会拒绝未注册工具、非法模板和非前序步骤引用；执行器只允许通过注入的统一 Runtime 回调调用工具，并新增有界包 codec 与测试源码。当前尚未接入产品 UI、插件包安装/启用注册、持久化版本仓库、签名、升级、撤销和回滚，因此还不能称为完整的自主插件商店/生命周期。

## 八、Android 系统助手入口

- Android 允许符合条件的应用申请 `ROLE_ASSISTANT`。应用可以实现 `VoiceInteractionService`，也可以处理 `Intent.ACTION_ASSIST` 以满足助手角色入口要求；是否可申请必须运行时检查，最终由系统角色选择界面和设备厂商实现决定。
- 本轮在 Manifest 声明 `ACTION_ASSIST`，MainActivity 从系统助手入口回到 Nestro 主聊天页，设置页增加运行时检查和系统确认式角色申请。这只是系统调用入口的第一步，不等于已实现常驻热词监听、锁屏语音交互、屏幕上下文理解或所有 OEM 的助手替换。
- 完整系统助手体验仍需评估 `VoiceInteractionService` / `VoiceInteractionSessionService`、系统触发方式、前台服务限制、隐私提示和不同厂商 ROM 兼容。常驻 VoiceInteractionService 必须保持轻量，重任务放在会话服务/实际交互阶段。
- 系统助手接入不应强制用户授权无关权限；读取屏幕、通知、无障碍操作等能力仍需单独说明、由用户自行启用，并经统一权限路由控制。
